# Phase 8 MiniCourse：Redis 缓存、限流与幂等加速

> 目标：面试时既能解释“为什么引入 Redis”，也能说清楚 Redis 故障时系统如何保持正确。

## 1. Redis 是派生状态，MySQL 是唯一事实来源

聊天记录必须先写入 MySQL。Redis 只保存最近消息、限流计数和幂等摘要，不能成为聊天记录的唯一副本。

最近消息采用 Cache-Aside：先校验会话归属，再读缓存；缓存缺失、损坏或版本不兼容时查询 MySQL，并回填最多 10 条消息。这样即使 Redis 数据被清空，业务数据仍可恢复。

面试要点：缓存提升性能，不改变数据所有权；正确性来自 MySQL，Redis 只降低重复查询成本。

## 2. 固定窗口限流必须是原子操作

聊天限流规则是每个用户每分钟最多 20 次。`INCR` 和首次设置 TTL 必须在同一个 Redis Lua 脚本中完成，否则并发请求可能留下没有过期时间的计数器。

第 21 次请求返回 HTTP 429，并携带 `Retry-After`。限流检查发生在创建请求记录、写入用户消息和调用 Python 之前。Redis 不可用时限流选择 fail-closed，返回 503，避免在失去保护时继续放大下游压力。

面试要点：原子性解决并发竞态；fail-open/fail-closed 是按风险选择，不是统一答案。

## 3. 缓存失效必须发生在数据库事务提交之后

写聊天数据时先提交 MySQL，再删除最近消息缓存。若在事务提交前删除，其他线程可能在旧事务尚未提交时回填旧数据，形成脏缓存。

缓存删除失败不能回滚已提交的 MySQL 事务。系统记录日志与指标，依靠较短 TTL 最终修复；下一次读缓存仍要具备回源能力。

面试要点：事务只能保证数据库内部一致性；跨 MySQL/Redis 使用“提交后失效 + TTL 兜底”，不引入分布式事务。

## 4. 幂等采用 Redis 加速与 MySQL 最终约束

Redis 幂等键保存 `requestId`、`requestHash`、状态和更新时间，TTL 为 24 小时。命中 Redis 后仍需确认 MySQL；缓存未命中则直接查询 MySQL。

同一个幂等键和相同请求体返回原结果；相同键但不同请求体返回冲突。Redis 故障时回退 MySQL，数据库唯一约束 `(user_id, idempotency_key)` 是并发场景下的最终防线。

面试要点：缓存命中不是事实确认；应用层检查改善错误语义，数据库唯一约束保证最终正确。

## 5. Key、TTL 与序列化格式也是接口契约

Key 使用 `iap:{env}:v1:<domain>:<purpose>:<identifier>`，包含环境和版本，避免跨环境污染并支持格式演进。用户提供的幂等键先做 SHA-256，再进入 Redis Key；不把消息正文、JWT、密码或文件内容放入 Key。

每类短期 Key 都必须设置 TTL：最近消息 30 分钟、限流计数 120 秒、幂等摘要 24 小时。JSON 数据读取时校验结构和版本；坏 JSON 应删除或忽略并回源 MySQL，而不是让缓存污染业务响应。

面试要点：Key 命名、TTL、序列化和兼容策略共同构成可维护的缓存协议。

## 快速自测

1. 为什么 Redis 命中后仍不能直接认定幂等请求存在？
2. 为什么缓存删除要放在 MySQL 提交之后？
3. `INCR` 与 `EXPIRE` 分开执行会产生什么并发问题？
4. 为什么限流 Redis 故障选择 fail-closed，而幂等缓存故障选择回退 MySQL？
5. 如何证明 Redis 中所有短期 Key 都有 TTL，而不是只验证代码调用过 `expire`？
