# Codex 协作流程

> 本文件解释本仓库的阶段协作方式。长期约束以根目录 `AGENTS.md` 为准；本文件不替代未来冻结的 `docs/ARCHITECTURE.md`。

## 1. 阶段边界

- 同一时间只处理一个 Phase。
- 未经用户明确批准，不进入下一道门，也不进入下一 Phase。
- 当前 Phase 以外的问题记录为技术债，不顺手重构。
- 若需要改变已冻结架构，必须先说明原因、影响范围、收益、成本、替代方案及兼容性，等待批准。

## 2. 三道门

### 门 1：阶段开始

1. 读取 `AGENTS.md`、`docs/ARCHITECTURE.md`（存在且已冻结时）、相关设计文档和真实源码。
2. 检查并报告 Git 分支、状态和现有差异。
3. 输出本阶段计划、修改/不修改文件、验收标准。
4. 先生成 MiniCourse。
5. 暂停等待首次批准。

### 门 2：Skeleton Review

首次批准后只建立接口、文件骨架和测试矩阵，不完成业务实现，不把占位内容伪装成可用功能。完成后暂停等待再次批准。

### 门 3：实现与验收

再次批准后才允许：

1. 完成实现；
2. 执行构建和测试；
3. 检查正常与异常流程；
4. 生成调用图；
5. 执行功能、架构、设计、生命周期四维审计；
6. 生成本 Phase Learning Kit；
7. 暂停等待 Review。

存在未解决的 `ERROR` 时不得进入下一 Phase。

## 3. Git 安全

- 每个 Phase 使用独立分支。
- 修改前执行并检查 `git status`、当前分支、`git diff --stat` 和 `git diff`。
- 用户已有的未提交修改必须保留；只精确暂存本 Phase 已验收内容。
- 不执行 `reset`、`clean`、`checkout --` 等破坏性命令，不重写历史。
- 每个通过验收的 Phase 建立独立提交；Review 前不擅自提交实现。
- 未经用户要求不 push。
- 密钥、Token、密码、真实用户数据、本地绝对路径、模型权重、checkpoint 和真实索引不得提交。

## 4. 证据要求

- 文档事实以源码、Git 历史或实际命令结果为依据。
- 未执行的验证必须写明具体阻塞原因，不能写成“已通过”。
- 测试必须被测试框架真实收集和执行；禁止 `assert True`、只打印结果或依赖导入副作用的伪测试。
- 测试命令需记录退出码、通过/失败/跳过数量；外部 API、模型和索引访问必须明确区分在线验证与离线验证。

## 5. Phase 0.5 的临时说明

`docs/ARCHITECTURE.md` 将在 Phase 1 冻结，因此 Phase 0.5 只稳定现有 Python 基线，不定义目标双服务架构。若本阶段发现迁移边界问题，只记录到 `docs/TECH_DEBT.md` 或报告架构风险。
